# 策略与实验结论

## 规则与执行模型

棋盘为16×10个1～9的数字。一次拖动选择一个矩形，其中尚未消除的数字总和为10则消除，每个数字计1分；空格可包含在矩形里，其余数字位置不变。160分意味着清空全部数字。

程序先识别完整棋盘，用C++搜索整条路径，再由Swift独立回放每个矩形，检查边界、数字和与得分。运行时将矩形换算为屏幕坐标，以10个线性小段拖动鼠标，每段约8毫秒；每步之后核对所有空位及剩余数字图像，每10步和最后一步进行完整OCR。不确定时回退OCR，只有原棋盘完全未变化才重试拖动。

## 已实现的搜索策略

| 名称 | 内容 / 当前定位 |
| --- | --- |
| `baseline` | 完整路径随机重启，偏好较大数字平方和，同时探索消除数量与随机扰动 |
| `repair` | 从较优路径保留前缀，扰动部分动作，再保留仍合法的旧动作 |
| `neighborhood` | 删除部分旧分组再重建；保留作实验对照 |
| `fastrepair` | 用插值表加速随机评分，保留原随机抽样语义 |
| `tailrepair` | 路径修复加局末小规模搜索；缓存已完整求解的残局 |
| `portfolio` | 四路搜索组合，共用一个墙钟预算 |
| `portfolio8` | 默认，四路路径修复加四路局末搜索，共用预算并取最高分路径 |
| `perfect8` | 实验：六路常规搜索、一路满分约束随机搜索、一路束搜索；仅符合必要条件时启用专用路线 |

搜索还使用较优终局去重、保留64条候选轨迹和退火探索。多线程不会将单局预算乘以线程数。`plan.json` 保存各线程得分、获胜种子及算法名称。达到可证明的分数上界时提前停止；否则限时搜索不保证全局最优。

## 满分必要条件

满分筛选不依赖游戏内部数据，只使用完整识别的数字：

- 总和必须被10整除。每组至少两个数字，故总和不能超过数字个数的5倍。
- 每个9必须配一个1；8需要2或两个1；7需要3或至少一个1。
- 较大数字所需的补数，只能由足够数量与总和的小数字提供。
- 奇数个5中，至少一个需要由1～4凑出另一个5。
- 可以先在数学上抵消所有互补对。若两数原属不同的和10组，其余数字可合成另一个和10组；抵消后每组至少三个数字，因此剩余数量不足时可排除满分。

这些是必要条件，忽略位置。通过筛选不代表存在合法矩形消除顺序。条件失败时，游戏内确认放弃并重新开始，约16秒可换一张棋盘。核查脚本用Ruby独立计算不可能满分的理由。

`full_clear_only` 与必要条件不同：60秒内没有搜到完整路径时可以重开，但记录为“预算内未找到”，不声称已经证明不可能。所找到的部分计划单独保存并核验，不计实测成绩。

## 采用与未采用的方案

早期对照支持路径修复与八路组合：八路对四路的两批12张同预算棋盘对照中，5张提高、7张持平，平均提高0.75分。不同随机棋盘的实际分数不能直接用于算法优劣比较。

路径共享、稀缺数字混合评分及若干组合候选在保留样本中出现回退，没有作为默认方案。满分约束搜索和束搜索在后续实验中也未显示胜过常规组合的证据。束搜索保留64～128个不同局面；额外的孤立数字覆盖评分降低了对照中的该路得分，因此未采用。

159分棋盘的最优分数早停，在同种子离线复现中约1.15秒找到159分；原实战该局使用了约32秒搜索。离线加速数据与原实战耗时须分别看待。合成棋盘测试得到160分也不等于真实游戏取得160分。
